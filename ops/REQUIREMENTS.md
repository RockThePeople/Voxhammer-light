# VoxHammer 편집 경량화 구축 요구사항서

Oct 18, 2026 · @Alex

## 1. 개요

여러 사용자가 하나의 3D 에셋을 반복 편집하는 시스템을 위해, VoxHammer 기반 편집 1회의 대기 시간을 최소화하는 새 구축을 요청합니다. 기존 개선분 중 검증된 것은 그대로 채택하고, 결과를 바꾸지 않는 개선을 우선 구현합니다.

**현황.** 기존 개선 경로(SLat 재사용 + cfg=0 게이트)의 편집 1회는 A5000 실측 116–129 s이며, 그중 편집 단계(inversion + denoising)가 약 92 s입니다. 기록상 이 수치에는 조건 렌더(Blender)와 인페인팅이 들어있지 않고, 두 단계의 시간은 측정된 적이 없습니다. 원 VoxHammer 경로는 259–278 s였습니다.

**목표.**

- 편집 결과를 현재와 같게 유지하면서 편집 1회의 벽시계 시간을 최소화한다
- 편집마다 반복되는 모델 로드, 중복 계산, CPU↔GPU 캐시 전송을 없앤다
- 편집 결과를 GLB 없이 `.cbin` 청크로 직접 만들고, 바뀐 청크만 Unity에 in-place로 교체한다

**범위.** A5000의 TRELLIS 생성·편집 서비스, 3090의 인페인팅 서비스, 두 서비스 간 전송, 편집 결과의 `.cbin` 변환까지입니다. Unity 클라이언트는 고정 시점 렌더 캡처(R10)만 범위에 포함합니다.

## 4. 요구사항과 진행 순서

요구사항은 아래 순서표의 번호 순서대로 하나씩 구현하고, 하나를 끝낼 때마다 그 항목만 검증해 보고합니다. 다음 항목은 고객사가 확인한 뒤 시작합니다. 이 장이 작업 지시의 유일한 기준입니다.

### 4.1 진행 규칙

1. **한 번에 한 항목.** 구현 → 단독 검증 → 보고 → 고객사 확인 → 다음 항목 순서를 지킵니다. 여러 항목을 묶어 구현하거나 한꺼번에 제출하지 않습니다.
2. **단독 검증.** 항목마다 환경변수로 켜고 끄게 만듭니다. 직전까지 승인된 상태를 기준으로, 해당 항목만 켠 결과와 띈 결과를 비교합니다. 승인되면 그 상태가 다음 항목의 기준이 됩니다.
3. **보고 내용.** 항목마다 6장의 구간 시간, 메모리, 동등성(결과 동일 항목) 또는 품질 지표(결과 변경 항목), 변경 파일 목록을 제출합니다.
4. **점수.** 용이도는 구현이 쉽고 처음부터 맞게 구현될 가능성이 높을수록 10점, 기대효과는 편집 시간 단축이 클수록 10점입니다. 효과는 구간 실측이 없는 상태의 고객사 추정치이며, 0번 착수에서 다시 매깁니다. 평균 6.0 이상은 1순위, 5.0–5.9는 2순위, 5.0 미만은 3순위입니다.
5. **연관 항목.** 따로 동작할 수 있는 항목은 분리해 각자 점수로 배치했습니다. 따로 동작할 수 없는 항목(R5-1 + R5-3, R4와 렌더 입력 교체)은 평균으로 배치했습니다. 순서표의 선행 항목이 승인되기 전에는 해당 항목을 시작하지 않습니다.
6. **2·3순위 진입.** 1순위가 끝난 뒤 계측에서, 항목이 줄이는 구간이 편집 1회 시간의 10% 이상일 때만 고객사 승인을 받아 진행합니다. 조건에 못 미치면 1순위 결과를 최종으로 합니다. 3순위는 고객사가 별도로 요청할 때만 진행합니다.
7. **품질 게이트.** 결과가 바뀌는 항목은 기본값으로 켜지 않습니다. 6장 품질 지표가 기준보다 나빠지면 기본값을 원복하고 결과만 보고합니다. 채택은 고객사가 결정합니다.
8. **구현 방식.** VoxHammer f33cd96 + 기존 패치를 포크해 고정하고, 동등성 비교의 기준 구현으로만 씁니다. 포크는 고치지 않습니다. 모든 구현은 4.2 지침에 따라 모듈별로 새 패키지에 가져와 다시 빌드합니다. TRELLIS 모델 코드는 VoxHammer 동봉본을 그대로 씁니다.

### 4.2 구현 지침: 모듈별 이식

VoxHammer 포크는 고치지 않고 정답 비교용으로만 둡니다. 편집 경로는 새 패키지에 모듈 단위로 가져와 다시 빌드합니다.

1. **포크의 역할.** f33cd96 + 기준 패치를 고정한 읽기 전용 기준 구현입니다. 허용되는 것은 포크 밖에서 호출 시간을 재는 계측 래퍼뿐입니다. 4.4–4.6에 적힌 함수 이름과 행 번호는 원본 동작의 위치를 가리킬 뿐이고, 수정은 항상 새 모듈에서 합니다.
2. **새 패키지.** `ai-ar-v3`에 별도 패키지(예: `editcore/`)를 둡니다. 모듈 구성은 아래를 기준으로 수행사가 확정합니다.

| 모듈 | 내용 | 원본 위치 |
| --- | --- | --- |
| `models` | 모델 로드. VoxHammer 동봉 `trellis/`를 수정 없이 import하고 같은 체크포인트 사용 | `trellis/` |
| `preprocess` | 조건 이미지 전처리(rembg, 공동 bbox crop, 518 리사이즈, DINOv2) | `preprocess_image` |
| `masks` | 3D·latent·KV·이미지 패치 마스크, 보존 좌표 판정 | `ply_to_ss_mask`, `ply_to_slat_mask`, `run_edit` 일부 |
| `cache` | K/V·잠재 저장소. 키 규칙, 저장 위치(CPU/GPU), 해제 | `ss_kv`·`slat_kv`·`latent` 딕셔너리 |
| `attention` | Stage 1·2 self·cross attention과 캐시 교체 | `ss_attn_forward`, `slat_attn_forward` |
| `blocks` | Transformer 블록과 flow 모델 순전파 | `ss_trsfmr_forward`, `ss_flow_forward`, `slat_trsfmr_forward`, `slat_flow_forward` |
| `sampler` | inversion·denoising 샘플러 | `InversionFlowEulerGuidanceIntervalSampler` |
| `pipeline` | 편집 1회 흐름(Stage 1 → Stage 2 → 출력) | `sample_*_inverse/denoise`, `run_edit` |
| `export` | SLat 저장, GLB(0-1번까지), `.cbin` 변환(2번부터) | `run_edit` 끝부분, `contract/` |
| `render` | 조건 렌더와 2D 마스크 | `utils/render_rgb_and_mask.py` |
| `service` | 상주 워커와 큐 | 없음(신규) |

3. **이식 방식.** 원본 함수를 옮긴 뒤, 동작을 바꾸지 않은 상태에서 동등성 테스트를 먼저 통과시킵니다. 개선은 그다음 플래그로 넣습니다. 옮긴 코드에는 출처(파일·함수·rev)를 주석으로 남기고, VoxHammer(MIT)와 TRELLIS 라이선스 고지를 유지합니다.
4. **구조 원칙.**
   - 원본의 `MethodType` forward 교체를 쓰지 않습니다. 블록·attention을 감싼 명시적인 클래스로 만듭니다.
   - 호출 사슬 전체를 관통하던 인자(캐시, 마스크, `t_latent`, `order`, `pos`, `layer`)는 하나의 편집 컨텍스트 객체로 넘깁니다.
   - 하드코딩 상수(4096·16·64, 37·14, 1374 = 5 + 1369)는 모델 설정에서 유도하되, 현재 모델에서 원본 값과 같은지 테스트로 확인합니다.
   - 전역 상태(grad 설정, rembg 세션 생성, 파일 경로 입출력)를 계산 함수 안에 두지 않습니다. 파일 입출력은 `service`와 `export`에만 둡니다.
5. **이식 시 반드시 보존할 동작.** 아래가 원본과 다르면 편집 결과가 바뀝니다.
   - 캐시 키 대응: inversion은 `t_prev`, denoising은 `t_curr`로 같은 `t_latent`를 만든다.
   - 2차 solver의 order 1·2를 따로 캐시한다.
   - CFG 구간 \[0.5, 1.0\], `rescale_t` 3.0, 스텝 25(1번 E2a 전까지), W38 cfg=0 게이트.
   - Stage 1 출력 voxel 병합(`voxel * voxel_mask + voxel_src * (1 - voxel_mask)`)과 Stage 2 보존 feats 최종 덮어쓰기.
   - 보존 좌표 판정은 D51 방식(정수 부호화). Stage 2 inversion은 보존 좌표로 자른 SLat으로 수행.
   - `preprocess_image`의 원본·편집 이미지 공동 bbox crop, 이미지 패치 마스크의 CLS·register 5개 토큰 처리.
   - SLat 재사용 입력(W34)과 `slat_space=denormalized` 검사.
6. **동등성 테스트 단위.** (a) 함수 단위: 같은 입력에서 포크 함수와 이식 함수의 출력 비교(축소 모델 CPU, 고객사 검증 스크립트 방식). (b) 단계 단위: Stage 1 결과 coords, Stage 2 결과 feats. (c) 종단: 같은 자산·마스크·조건에서 6장 허용치. 테스트는 저장소에 넣고, GPU 없이 도는 CPU 판을 포함합니다.
7. **순서.** 순서표 0-1번에서 개선 없이 편집 경로 전체를 이식해 종단 동등을 확인한 뒤 1번부터 개선을 시작합니다. 한 항목의 개선은 해당 모듈만 고칩니다.

### 4.4 1순위 항목별 지시

#### 0. 착수

- **요구.** VoxHammer f33cd96 + 기준 패치를 포크해 고정하고 그대로 실행한다. D51·W34·W38(R1–R3)은 유지하고 W39 코드는 제거한다(5장).
- **SLat 포획(R2).** 편집 래퍼에서 `slat_tgt`를 매 편집 `safetensors`(coords int32 (N,4), feats float32 (N,8), 메타 `slat_space=denormalized`)로 저장해 다음 편집 입력으로 쓴다. 옵션이 아니라 기본 동작이다.
- **in-place 구조 유지(R11).** A5000 편집 서비스가 점유 비교로 바뀐 청크를 정하고 나머지는 부모 `.cbin` 바이트를 승계한다. 3090은 계약 판본 검증 후 저장하고, Unity는 changed 교체·removed 파괴·새 키 생성을 한다. 변경 청크를 해시로 정하지 않는다(전역 디코딩 때문에 절감이 0%가 됨).
- **검증 스크립트.** 고객사 스크립트 3개(`v_stage1_cache.py`, `v_stage2_misc.py`, `v_cbin_direct.py`)를 A5000에서 실행하고, 실제 규모(24블록, 1,024채널, 4,096토큰)로도 한 번 돌린다.
- **기준선.** 6장 구간 계측 기준선을 제출하고, 이를 근거로 순서표의 효과 점수를 다시 매긴다. 현재 편집 서비스가 모델을 이미 상주시키는지(4번 R8a 효과 0 여부)도 확인한다.
- **단독 검증.** conformance 53/53, 서버 테스트 전부 통과(현재 360개), 포크 실행 결과가 기존 실측(W41 자산)과 같은 자릿수인지.

#### 0-1. 모듈 이식

- **요구.** 4.2 지침대로 편집 경로 전체(모델 로드, 전처리, 마스크, 캐시, attention, 블록, 샘플러, 파이프라인, 출력)를 새 패키지로 이식한다. 개선은 넣지 않는다. 출력은 원본처럼 GLB까지 만든다(`.cbin` 직행은 2번 R4).
- **구현 지침.** 모듈 하나를 이식할 때마다 함수 단위 동등성 테스트를 붙이고 통과시킨 뒤 다음 모듈로 넘어간다. 권장 순서는 `masks` → `sampler` → `attention`·`blocks`(Stage 1) → `attention`·`blocks`(Stage 2) → `preprocess` → `pipeline` → `export`다.
- **단독 검증.** 함수 단위·단계 단위·종단 동등성(6장 허용치)과, 편집 시간이 포크와 같은 자릿수인지.
- **기대효과.** 시간 단축은 없다. 이후 모든 항목의 기반이다.

#### 1. E2a 샘플러 스텝 수 축소

- **요구.** `InversionFlowEulerGuidanceIntervalSampler.sample` 안의 고정값 `steps = 25`를 설정값으로 뺀다. 12, 15, 25 스텝을 비교한다.
- **구현 지침.** inversion과 denoising은 반드시 같은 스텝 수를 쓴다(캐시 키 `t_latent`가 일치해야 함). `rescale_t = 3.0`은 유지한다. Stage 1과 Stage 2를 따로 설정할 수 있게 한다.
- **단독 검증.** 25 스텝 대비 6장 품질 지표(보존 IoU, CLIP-I/DINO-I, 육안)와 편집 단계 시간.
- **기대효과.** forward 수와 캐시 전송이 스텝 수에 비례한다고 보면, 편집 단계 92 s가 12–15 스텝에서 37–48 s 줄어든다(추정). 결과가 바뀌므로 품질 게이트를 적용한다.

#### 2. R4 mesh만 디코딩 → `.cbin` 직행

- **요구.** `run_edit` 끝의 `decode_slat(slat_tgt, ["gaussian", "mesh"])` + `to_glb` + `export`를 `decode_slat(slat_tgt, ["mesh"])`로 바꾸고, `MeshExtractResult`의 vertices·faces·vertex\_attrs를 `split_trellis_vertex_attrs`(기본 `0_1`) → `albedo_to_rgba8` → `partition_mesh` → `encode`에 넘긴다.
- **구현 지침.** 좌표는 디코더 native라 `to_glb`의 회전을 걸지 않는다(D9-b). 디버그용 GLB는 `server/glbbuild.py`로 `.cbin`에서 조립한다.
- **렌더 입력 교체(분리 불가).** 다음 편집의 조건 렌더(Blender)는 GLB를 입력으로 받는다. R4 이후에는 `glbbuild`로 조립한 정점색 GLB가 입력이다. Cycles 재질이 정점색을 읽는지 확인한다. 회색으로 렌더되면 원본 조건 이미지와 인페인팅 입력이 모두 틀어진다.
- **메시 밀도.** `to_glb`의 단순화(`simplify=0.95`, 면 95% 제거)가 빠지므로 편집 청크가 커진다. 변경 청크 바이트, Unity 프레임 시간, 부모 청크의 면 수를 함께 보고한다.
- **단독 검증.** `slat_tgt` 비트 동일(디코딩 앞단 불변), 청크화·인코딩 시간(고객사 CPU 실험 16만 정점 1.4–1.6 s), Unity 육안 비교, 서버 테스트와 `tools/unity_inplace_check.sh` 통과.
- **기대효과.** W41 기준 편집 단계 밖 나머지 24–37 s 안에서 Gaussian 디코딩과 `to_glb` 몫이 줄어든다. `slat_to_glb` 46.4 s(W8)는 상한으로 쓰지 않는다.

#### 3. R10a 조건 렌더 축소

- **요구.** `utils/render_rgb_and_mask.py`는 원본 GLB와 마스크 GLB를 각각 5개 시점(1024², Cycles), 총 10회 렌더한다. 인페인팅에는 1개 시점만 쓰므로 그 시점만 렌더하고, 마스크 GLB는 depth만 출력한다.
- **구현 지침.** 카메라 행렬·해상도·환경맵은 기존 그 시점과 똑같이 둔다. Cycles 시드를 고정한다(기존 함정 8: 미고정).
- **단독 검증.** 시드를 고정한 기존 스크립트의 같은 시점 이미지·2D 마스크와 비교(동일 또는 차이 보고), 렌더 시간.
- **기대효과.** 렌더 10회 → 2회. 시간은 미측정.

#### 4. R8a A5000 편집 워커 상주

- **요구.** TRELLIS 모델(두 flow, SS 인코더·디코더, SLat mesh 디코더, DINOv2)을 프로세스 시작 시 1회 로드하고, 편집 요청을 단일 큐로 받아 이식한 편집 파이프라인(원본 `run_edit`에 해당)을 반복 호출한다.
- **grad 상태.** 원본 `run_edit`는 끝에서 `torch.set_grad_enabled(True)`를 켜 둔 채 끝난다. 이 호출을 없애고 요청마다 `torch.inference_mode()`로 감싼다.
- **요청 간 정리와 동시성.** 편집이 끝나면 K/V 캐시와 중간 텐서를 해제한다. 편집 1회 CPU RSS가 약 74 GiB(기존 실측)라 124 GB 호스트에서 동시 편집은 1건만 가능하다. 큐 대기 시간을 따로 기록한다. 같은 에셋은 판본 순서대로 처리하고, 기준 판본이 다르면 기존 409 `VERSION_CONFLICT` 규약을 따른다.
- **단독 검증.** 같은 입력으로 3회 연속 요청했을 때 결과가 허용치 안에서 같고, 2·3회차 RSS·VRAM이 1회차와 같은 수준으로 돌아오는지. 모델 로드 시간과 요청당 시간.
- **기대효과.** 실행마다 반복되던 모델 로드 제거. 현재 서비스가 이미 상주면 0.

#### 5. R9 3090 INT4 FLUX Fill 상주

- **요구.** `nunchaku-ai/nunchaku-flux.1-fill-dev`(INT4)를 별도 venv(Nunchaku 요구 torch·CUDA 버전)의 상주 프로세스로 띄운다. 호출마다 subprocess를 띄우지 않는다.
- **입출력.** 입력은 원본 렌더(기존 Blender 렌더의 사용 시점 1장), 2D 마스크, 프롬프트, 시드. 출력은 `2d_render.png`·`2d_mask.png`·`2d_edit.png` 3종이다. HTTP로 A5000에 보낸다(기존 multipart `meta` + `image` 규약 확장).
- **마스크 밖 합성.** 마스크 밖 픽셀은 원본 렌더로 다시 합성한다. cross-attention 마스크가 `2d_mask`를 37×37 패치로 읽기 때문이다.
- **설정.** 이 항목에서는 해상도·스텝을 기존값(1024², 50스텝, guidance 30)으로 둔다. 바꾸는 것은 6번 E4다.
- **3090 VRAM.** 3090은 신규 에셋 생성용 Z-Image-Turbo도 돌린다. 두 모델의 동시 상주 가능 여부를 측정하고, 24 GB를 넘으면 Z-Image 4-bit 또는 생성 요청 때만 교대 로드를 제안한다. 편집 인페인팅이 우선이다.
- **단독 검증.** 기존 bf16 FLUX(CPU offload) 대비 같은 시드의 인페인팅 이미지와 3D 편집 품질, 인페인팅 시간, A5000에서 서비스 언로드·재기동이 사라졌는지.
- **기대효과.** A5000의 FLUX CPU offload와 편집 서비스 재기동 제거, INT4 가속.

#### 6. E4 인페인팅 해상도·스텝 축소

- **요구.** 객체 bbox(×1.2 정사각, VoxHammer `preprocess_image`와 같은 규칙) 영역을 512 / 768 / 1024로 생성하고, FLUX Fill 스텝 수도 함께 비교한다. TRELLIS는 최종적으로 518×518을 쓴다.
- **정렬 규칙.** 잘라 생성한 결과는 원래 캔버스의 같은 위치에 되붙여 `2d_render`·`2d_mask`·`2d_edit` 세 장이 같은 크기·같은 픽셀 격자를 유지해야 한다. `preprocess_image`가 세 장에 같은 crop을 적용하기 때문이다.
- **단독 검증.** 해상도·스텝별 인페인팅 시간과 3D 편집 품질. 결과가 바뀌므로 품질 게이트를 적용한다.

#### 7. R8b rembg 세션 재사용

- **요구.** `preprocess_image`의 `rembg.new_session("u2net")`(편집당 2회 생성)을 모듈 전역 세션 1개로 바꾼다. 배경 제거 호출 두 번(원본·편집 이미지)은 그대로 둔다.
- **단독 검증.** 전처리 출력 이미지 비트 동일, 전처리 시간.

#### 8. R12 cross K/V 중복 저장 제거

- **요구.** `ss_attn_forward`(패치 적용 후 198–199행)와 `slat_attn_forward`(315–316행)의 cross-attention K/V 저장 키에서 `t_latent`·`order`를 빼고 (pos, layer)당 1회만 저장한다. 이미 있으면 다시 저장하지 않고, 편집 패스는 그 하나를 읽는다.
- **근거.** cross K/V는 `to_kv(cond)`로만 계산되며 현재 잠재·타임스텝과 무관하다. 고객사 실험에서 모든 t·order의 값이 비트 동일했고, 1회 저장판의 최종 결과도 비트 동일했다.
- **단독 검증.** 최종 결과 동일(허용치), 캐시 딕셔너리 용량과 CPU RSS, 캐시 저장·적재 시간.
- **기대효과.** cross 캐시 Stage 1 약 11.9 → 0.27 GB, Stage 2 약 6.75 → 0.13 GB(계산치). CPU RSS 약 18 GB 감소, inversion·denoising의 CPU↔GPU 동기 전송 약 18.6 GB씩 제거. 시간은 미측정.

#### 9. R7g Stage 2 매칭 불일치 검사

- **요구.** 편집 시작 시 보존 좌표가 현재 토큰과 캐시 토큰에 모두 있는지 검사하고, 없으면 불일치 개수를 담은 오류로 중단한다. 원본 `match.float().argmax(0)`는 불일치 시 0번 토큰을 조용히 덮어쓴다(고객사 재현).
- **단독 검증.** 정상 자산에서 통과하고 결과가 비트 동일, 존재하지 않는 좌표를 넣으면 중단.
- **기대효과.** 시간 효과 없음. 결과가 몰래 틀어지는 경우를 오류로 드러낸다.

### 4.5 2순위 항목별 지시

1순위가 끝나고 4.1의 진입 조건을 만족한 항목만, 고객사 승인 후 진행합니다. 10번과 11번은 동시에 쓸 수 없으므로, 1순위 후 계측(Stage 1 inversion 시간 대 캐시 전송 시간)을 근거로 하나만 고릅니다.

#### 10. R5-1 + R5-3 Stage 1 보존 토큰만 저장 + 캐시 GPU 상주

- **요구(R5-1).** 편집 패스는 self-attention 캐시에서 `kv_mask = 0`인 행만 읽는다. inversion 전에 이미 계산되는 마스크로 보존 토큰 인덱스를 만들고 그 행의 K/V만 저장한다. 대입은 `k[:, :, idx] = cached`로 한다.
- **요구(R5-3, R5-1 없이는 불가).** 캐시가 VRAM에 들어가면 GPU에 상주시켜 `.cpu()`/`.cuda()` 전송을 없앤다. 기존 편집 피크 14,180 MiB에 캐시를 더해 24 GB 안에 드는지 확인하고, 들어가지 않는 자산은 pinned memory + non\_blocking 전송으로 대체한다. Stage 1 캐시는 Stage 2 시작 전에 해제한다.
- **단독 검증.** R5-1과 R5-3을 따로 켜고 끄며 각각 최종 결과 동일(허용치), 캐시 용량, VRAM 피크, 전송 시간. 보존 토큰 비율은 자산·마스크마다 다르므로 자산별로 보고한다.
- **고객사 검증.** CPU 축소 모델에서 보존 행 K/V + cross 1회(R12) 저장 시 캐시 11.9%, 최종 z 비트 동일.
- **기대효과.** moto 자산(보존 토큰 546/4,096) 기준 Stage 1 self 캐시 약 35.4 → 약 4.7 GB(추정). GPU 상주 시 Stage 1 캐시 전송 제거.

#### 11. E3 커밋 직후 Stage 1 inversion 미리 계산

- **요구.** 판본이 커밋되면 백그라운드로 Stage 1 inversion을 돌려 둔다. Stage 1 inversion은 마스크와 무관하다(코드 확인). 마스크를 아직 모르므로 전체 토큰을 저장해야 하고, 그래서 10번과 함께 쓸 수 없다.
- **전제.** `cond_src`(원본 조건 이미지)가 에셋별 고정 시점이어야 한다. 새 판본이 커밋되면 이전 결과는 폐기한다.
- **단독 검증.** 미리 계산한 결과를 쓴 편집과 즉시 계산한 편집의 결과 동일(허용치), 사용자 대기 시간, CPU RSS. 같은 판본에 편집이 여러 건일 때 공유되는지.

#### 12. R7 Stage 2 매칭 인덱스 편집당 1회

- **요구.** 현재 `slat_attn_forward`는 블록마다, forward마다, K와 V 각각 (N×M) 좌표 비교를 다시 한다(편집당 약 2,400회). 편집 시작 시 32³ 좌표를 정수 하나로 부호화하고 정렬 + `searchsorted`로 인덱스를 구해 모든 블록에서 재사용한다. 9번 검사를 그대로 포함한다.
- **단독 검증.** 최종 결과 비트 동일, Stage 2 시간, 임시 텐서 VRAM.
- **고객사 검증.** 비트 동일, CPU에서 원본 1회 125 ms·임시 텐서 약 44 MB → 인덱스 계산 0.9 ms 1회.

#### 13. E1 Stage 1 CFG 배치화

- **요구.** CFG 구간의 조건/무조건 forward를 배치 2로 1회 호출한다. 캐시 키의 `pos`를 배치 축 인덱스로 바꾼다.
- **단독 검증.** 비트 동일이 아니다(고객사 CPU 실험 max|Δ| 1.4e-6). 허용치 안인지, Stage 1 시간, VRAM 피크.

#### 14. E2b denoising Euler화

- **요구.** denoising을 1차 solver로 바꾼다. inversion과 캐시 키(`order`, `t_latent`)를 다시 맞춘다.
- **단독 검증.** 1번에서 승인된 스텝 수 기준 품질 지표와 시간. 결과가 바뀌므로 품질 게이트를 적용한다.

### 4.6 3순위 항목별 지시

고객사가 별도로 요청할 때만 진행합니다.

#### 15. R10 고정 시점 렌더러 교체

- **요구.** 에셋별 기준 카메라를 저장하고, Blender 대신 (a) Unity 고정 카메라 `RenderTexture` 캡처(기존 `LassoCase.BuildCamera` 기반) 또는 (b) A5000에서 `.cbin` 메시를 nvdiffrast로 렌더하는 안 중 하나를 근거와 함께 제안한다. 2D 마스크는 마스크 복셀을 같은 카메라로 투영해 만든다. 클라이언트가 준 복셀이 유일한 기준이며, 조건 이미지 좌표로 3D 마스크를 다시 만들지 않는다.
- **함께 검토.** 렌더가 알파를 직접 내면 원본 렌더의 배경 제거를 생략할 수 있다. 결과가 바뀌므로 품질 게이트를 적용한다.
- **단독 검증.** 기존 Blender 사용 시점과의 정렬(같은 카메라에서 실루엣 IoU), 렌더 시간, 3D 편집 품질.

#### 16. R5-2 Stage 1 projection 입력 캐싱

- **요구.** 10번 위에서 K/V 대신 self-attention 입력 `x`(adaLN 변조 후)의 보존 행만 저장하고, 편집 패스에서 `to_qkv` → reshape → `k_rms_norm`으로 K/V를 다시 계산한다. Stage 1은 APE라 RoPE 처리가 없다.
- **단독 검증.** 최종 결과 동일(허용치, fp16 부분 행 GEMM은 마지막 비트가 다를 수 있음), 캐시 용량, 재계산 시간.
- **고객사 검증.** CPU 축소 모델에서 캐시 5.9%, 최종 z 비트 동일. 실제 규모 약 2.8 GB(추정). 10번으로 GPU 상주가 이미 되면 시간 효과는 거의 없다.

#### 17. R6 Stage 2 projection 입력 캐싱

- **요구.** 16번과 같은 방식을 `slat_attn_forward`에 적용한다. Stage 2 inversion은 이미 보존 토큰만 다루고, cross 부분은 8번에서 처리된다. sparse 텐서라 `_linear`·`_fused_pre`·`q/k_rms_norm` 순서를 원본과 똑같이 재현하고, RoPE 사용 여부를 코드에서 확인해 보고한다.
- **단독 검증.** 최종 결과 동일(허용치), Stage 2 캐시 용량.

캐시 fp8 저장은 순서표에 없으며, 10번 적용 후에도 VRAM이 부족한 자산이 있을 때만 고객사가 별도로 요청합니다.

| 편집 경로의 BiRefNet | A5000이 rembg를 다시 돌려 알파를 덮어쓴다. 배경 제거는 R8의 단일 세션으로 한 번만 한다 |
| 발표자료 수치 기반 목표치 | 출처 미확인. 목표·비교는 6장의 신규 기준선 측정으로만 한다 |

## 6. 계측·검증·인수 기준

구현에 들어가기 전에 현재 경로의 구간 계측으로 기준선을 먼저 제출합니다(4장 0번 착수). 이후 4장 항목마다 같은 구간으로 재어 직전 승인 상태와 비교합니다. 현재는 편집 단계 92 s의 내부 분해가 어디에도 없습니다.

### 구간 계측

편집 1회를 다음 구간으로 나눠 기록합니다. 각 구간 경계에서 `torch.cuda.synchronize()` 후 시간을 잽니다.

1. 조건 렌더: Blender 프로세스 기동, 원본·마스크 렌더(시점 수·샘플 수를 함께 기록), 2D 마스크 후처리
2. 3090: 인페인팅(모델 상주 상태, 해상도·스텝 기록), 전송
3. A5000: 전처리(rembg, DINOv2)
4. Stage 1 inversion / denoising (각각 forward 연산, 캐시 저장·적재, 전송)
5. Stage 1 디코딩(점유 격자)
6. Stage 2 inversion / denoising (각각 forward 연산, 좌표 매칭, 캐시 저장·적재, 전송)
7. mesh 디코딩, `.cbin` 청크화·인코딩, 부기, 전송 (R4 전에는 Gaussian 디코딩과 `to_glb`를 따로)
8. 큐 대기, 모델 로드(상주 전후 비교용, 최초 1회만)

여기서 1–8의 합이 사용자 한 명이 체감하는 편집 시간입니다. 기존 116–129 s는 4–7만 포함한 값입니다.

### 메모리 측정 규칙

- VRAM은 구간마다 `torch.cuda.reset_peak_memory_stats()` 후 `max_memory_allocated()`를 기록한다. 프로세스 전체 피크만 적은 기존 수치는 어느 단계 값인지 구분되지 않았다.
- `nvidia-smi` 값은 CUDA 컨텍스트와 할당기 캐시를 포함하므로 별도 열로 적는다.
- CPU는 프로세스 RSS 피크와 캐시 딕셔너리 용량(텐서 바이트 합)을 따로 적는다.

### 동등성 허용치 (결과 동일 항목)

같은 자산, 같은 마스크, 같은 조건 이미지, 같은 시드로 변경 전후를 비교합니다.

| 대상 | 합격 조건 |
| --- | --- |
| Stage 1 결과 coords (점유) | 완전 일치. 불일치 시 뒤집힌 셀 수와 마스크 경계까지의 거리를 보고하고 고객사가 판정 |
| Stage 2 결과 feats | max\|Δ\| ≤ 4.7e-2 (기존 실측 CUDA 비결정성 바닥값). 동일 코드 2회 실행의 차이도 함께 보고 |
| 보존 영역 청크 | 승계 바이트 동일, 변경 청크 수 보고 |
| 서버·계약 테스트 | conformance 53/53, 서버 테스트 전부 통과(현재 360개) |

고객사가 제공하는 검증 스크립트 3개(`v_stage1_cache.py`, `v_stage2_misc.py`, `v_cbin_direct.py`)를 A5000에서 실행해 GPU fp16 결과를 제출합니다. 실제 모델 규모(블록 24, 채널 1,024, 토큰 4,096)으로도 한 번 돌린다.

### 품질 지표 (E1–E4, R4 육안 비교)

- 보존: 고정 영역 채점(빈 칸 포함) 보존 IoU와 사라진 셀 수 (기존 `w42_region_eval` 기준)
- 편집: VoxHammer 논문 Table 1과 같은 CLIP-I / DINO-I
- 육안: 같은 시점·조명의 비교 렌더
- 마스크가 점유 셀로만 이루어진 경우의 "마스크 안 신규 = 0" 같은 정의상 성립하는 지표는 쓰지 않는다

### 대상 자산

t1s-snowman, t2s-moto(기존 W41·W42 자산) 2종 이상으로, 마스크 크기가 다른 편집을 각 2건 이상 실행합니다. 시간은 3회 실행 평균±표준편차로 적습니다.

## 7. 산출물과 보고 형식

### 산출물

- 소스 코드: A5000 편집·생성 서비스, 3090 인페인팅 서비스, 새 편집 패키지(4.2)와 동등성 테스트. 모두 `ai-ar-v3` 저장소에 커밋한다. VoxHammer 포크는 기준 패치 상태 그대로 두고 수정하지 않는다
- 실행 방법: 두 서비스의 환경(venv 버전), 환경변수 목록, 기동·재기동 절차
- 요구사항별 토글: 4장의 모든 항목은 환경변수로 끄고 켤 수 있어야 한다
- 테스트: 결과 동일 항목의 동등성 시험을 항목마다 저장소 테스트로 추가한다(축소 모델 CPU 판은 GPU 없이 돌아야 한다)

### 보고 형식

- 각 수치에 **실측 / 코드확인 / 추론 / 미검증**을 표시한다
- 실측에는 장비, 자산, 마스크 지문, 커밋, 실행 횟수를 적는다
- 변경 전후는 같은 자산 위에서만 비교한다(TRELLIS 생성은 같은 시드에서도 비결정적)
- 예상을 먼저 적고 결과를 적는다. 예상과 다르면 원인을 가른다
