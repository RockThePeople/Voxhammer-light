## 1. 예상 (구현 전)

- INT4 transformer(6.3 GiB) + T5·CLIP·VAE bf16 을 GPU 에 상주시키면 약 16 GiB 를 차지하고, 1024²·50스텝 호출 피크는 약 18 GiB 가 된다.
  - 근거: 기존 README 의 30스텝 피크 18.1 GiB(`미검증`).
- 호출당 시간은 30스텝 15.6 s 기준으로 50스텝이면 약 26 s 다(`추론`, 스텝당 약 0.5 s). 상주 덕분에 호출마다 들던 적재 비용은 없어진다.
- Z-Image(0번 B-3: 피크 alloc 21.67 GiB, nvidia-smi 23.3 GiB)와는 24 GiB 안에 같이 상주할 수 없다.
- 마스크 밖 합성 후 원본과 바이트가 같다. 합성 전에는 VAE 왕복 때문에 마스크 밖도 흔들린다.

- 따라서 R-4 는 "같은 시드 = 같은 그림" 을 전제할 수 없다. 기준(bf16) 대 INT4 차이를 판정할 때 **INT4 자기 반복 간 차이**를 바닥값으로 함께 재야 한다. 정오표 E7 의 방식(같은 코드 반복 분포)을 이미지에 적용하자는 제안이다.

## R-3 3090 VRAM (실측)

1. **동시 상주는 불가능하다.** 워커가 상주해 있고 호출 1회를 마친 상태(nvidia-smi 20,092 MiB)에서 Z-Image(`zimage_gen.py`, seed 42)를 띄우면 GPU 전송 중 `torch.OutOfMemoryError` 가 난다.
   - 그 시점 Z-Image 프로세스는 3.91 GiB, GPU 전체는 24,105 MiB 였다. 워커는 영향받지 않았다(`/health` 정상).
   - 워커가 막 뜬 상태(16.4 GiB)라도 Z-Image 의 적재 직후 19.28 GiB 를 더하면 24 GiB 를 넘는다.
2. **제안 (a) 생성 요청 때만 교대 로드 — 권장.** 워커 종료 → Z-Image 1회 → 워커 재기동(ready)을 3주기 실측했다(이 측정은 미러 경로, 파일은 원본과 동일).

   | 단계 | 시간 |
   |---|---|
   | 워커 종료(GPU 비움 확인까지) | 0.52 ± 0.07 s |
   | Z-Image 호출(subprocess, 0번 B-3 과 같은 래퍼) | 21.92 ± 0.28 s |
   | 워커 재기동 ~ ready | 7.36 ± 0.12 s |
   | **주기 합계** | **29.89 ± 0.28 s** |

   - Z-Image 출력은 3회 모두 0번 B-3 출력과 바이트가 같았다(`ba83d6d4…`). 교대해도 생성 결과는 바뀌지 않는다.
   - 생성은 자산 생성 때만 일어나고 편집 인페인팅이 우선이다. 그러니 "생성 요청이 오면 워커 큐가 빌 때까지 기다린 뒤 교대" 하는 정책이면, 생성 1건당 편집 경로가 막히는 시간은 최대 약 30 s 다.
   - 재기동 비용 중 GPU 전송 2.75 s 와 프로세스 시작·import 약 3.3 s 는 워커 안에서 `pipe.to("cpu")` 로 내렸다 다시 올리면 줄일 수 있다. 측정은 하지 않았다(`추론`).
3. **(b) Z-Image 4-bit — 단독으로는 부족하다(`추론`).**
   - `nunchaku-ai/nunchaku-z-image-turbo` 에 `svdq-int4_r32` 3.36 GiB(Apache-2.0, 비게이트)가 있고, 설치된 nunchaku 1.2.1 에 `NunchakuZImageTransformer2DModel` 이 있다. 새 설치 없이 시험할 수 있다.
   - 그러나 Z-Image 메모리의 나머지 큰 몫은 텍스트 인코더(Qwen3-4B bf16, 디스크 7.5 GB, 약 7 GiB)다. transformer 만 4-bit 로 바꾸면 적재 직후 약 11.9 GiB, 피크 약 14.3 GiB 로 추정한다. 워커 상주 16.4 GiB 와 더하면 24 GiB 를 넘는다.
   - 인코딩 뒤 텍스트 인코더를 CPU 로 내려야 겨우 약 23 GiB 다. 여유가 없다.
   - 가중치 3.4 GiB 를 받아야 해서 실측은 하지 않았다. 필요하면 실측하겠다.

## R-4 비교 — 입력 대기

A5000 이 `xfer/track-a-conditions` 로 보낼 트랙 A 6건의 `2d_render`·`2d_mask`·프롬프트와 bf16 기준 `2d_edit`(seed 0)을 기다린다. 받으면 다음을 잰다.
- 같은 입력·seed 0 으로 INT4 를 3회 실행: 위 재현성 문제 때문에 자기 반복 차이를 바닥값으로 쓴다.
- 인페인팅 시간(적재 1회 / 호출당), VRAM
- 마스크 안 PSNR·LPIPS·CLIP-T, 마스크 밖 합성 후 원본 일치 여부
- 6건 비교 시트(육안)

LPIPS·CLIP-T 는 `flux-fill` env 에 없다. Edit3D-Bench 평가 코드를 쓰는 A5000 venv 로 지표를 계산할지, 3090 에 별도 venv 를 만들지 정해야 한다(8절).

## 6. 예상과의 차이와 원인

- **같은 시드에서 INT4 출력이 비결정적이다**(위 R-2). 예상은 "같은 시드 = 같은 결과" 였다. 원인은 분리하지 않았다(`추론`: nunchaku 커널). R-4 판정 방식에 영향을 준다.
